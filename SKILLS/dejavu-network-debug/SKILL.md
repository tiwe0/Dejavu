# 网络请求路径排查

准备设备、精确进程名、一次可重复触发的测试请求，以及预期的收发方向和输出方式。测试请求使用已知的合成内容，便于对照长度和触发时间。设备与作用域操作沿用项目指南。[基础操作](../../SKILL.md)

## 排查流程

1. 用 `./dejavu status` 核对设备、模块、作用域和目标 PID，再用 `./dejavu exec -p PROCESS -e 'return 1'` 验证目标 Agent 的 RPC，替换 `PROCESS` 为本次进程名。确认请求实际发生的进程，包括独立网络进程的后缀。结合测试代码定位 Java 请求入口，必要时对该入口记录临时调用计数，保留本次安装的 Hook ID。[Java Hook 示例](../../zygisk/docs/cookbook.md)
2. 需要观察 TLS 边界时，按公开示例加载 `capture`，核对 `libssl.so` 的 `SSL_write` 和 `SSL_read` 是否可解析。加载成功和 `capture.start` 成功分别记录。[示例安装与调用](../../examples/capture/README.md)
3. 按用户需要选择下表的输出。若使用流，先运行 `capture.probe(transport, endpoint)`，在接收端看到 `dejavu-stream-probe` 后，再触发业务测试。该探针验证传输路径，其执行结果与实际 TLS 采集分开判断。
4. 启动采集，保存一份 `capture.status()` 基线，只触发一次测试请求，再读取状态并比较差值。计数在同一插件实例内跨 `start` 和 `stop` 保留，使用前后差值解释本次变化。[计数实现](../../examples/capture/plugin_entry.cpp)
5. 若 Java 入口命中而原生计数没有变化，核对实际使用的 TLS 库、进程和调用入口。当前样例覆盖解析到的两个 `libssl` 符号，其他实现或协议路径需要依据测试代码继续定位。

## 输出选择

| 需求 | 当前样例的用法 |
| --- | --- |
| 查看收发调用与字节计数 | 使用 `/dev/null` 作为 `capture.start` 的路径参数，读取前后状态差值。 |
| 查看实时合成数据 | 使用 `/dev/null` 路径并提供流传输类型和端点。查看器按用户要求保留内存输出。 |
| 保存本次测试记录 | 使用用户指定的可写路径，并记录该文件的保留与清理安排。 |

当前 `capture_record` 在文件描述符小于零时直接返回。因此，空路径启动虽会建立流，实际请求记录和计数仍会被跳过。源码允许把非空路径 `/dev/null` 打开为写入端，记录经过该路径丢弃，流与计数继续处理。先检查启动结果，再用合成请求验证所选输出。[输出实现](../../examples/capture/plugin_entry.cpp)

## 证据解释

- `OUT` 在调用原始 `SSL_write` 之前记录，字节数来自请求写入长度。写入成功与否还需结合原调用结果判断。
- `IN` 在 `SSL_read` 返回正长度后记录。调用次数反映 SSL 调用次数，和 HTTP 请求数、网络包数及整机吞吐量分别统计。
- 每条记录最多保留前 900 字节，并把非 ASCII 可打印字符替换为 `.`。HTTP/2、压缩、二进制和 Unicode 内容需要在对应协议层核对，截断记录不足以还原完整响应。
- `probe` 到达而测试请求没有记录时，分别报告“传输探针通过”和“指定 TLS 入口未取得本次证据”，继续检查进程、输出模式和库覆盖范围。[采集与探针实现](../../examples/capture/plugin_entry.cpp)

## 完成与清理

报告目标进程、测试触发条件、Java 与原生层各自取得的证据、计数差值，以及协议或采集覆盖的限制。取得足够证据后调用 `capture.stop()` 并卸载本次加载的插件，核对返回结果。只移除本次安装的 Java Hook，并关闭本次查看器。若创建了文件，按用户约定处理该文件。[插件卸载约定](../../zygisk/docs/plugin-api.md#unloading)
